# Architecture

## Repository

- `crates/kaalang-compiler/` parses and resolves flows into the shared validated
  semantic model, decides the diagram, exposes its common arrangement checks,
  and lowers the verified plan to Rust. It also parses type declarations and
  expands datatypes. Behind its `source` feature it reads flows and types from
  the text of a file for the renderers, which read no source themselves, says
  what each drawn element of a flow or a type stands for there, and lists where
  each flow and type is declared.
- `crates/kaalang-workspace/` reads a Cargo workspace for the diagrams: its
  targets in the order their cards stand, which file a module declaration loads,
  each target's module tree, and how Rust paths resolve across those trees. The
  compiler reads one source text and knows no workspace.
- `crates/kaalang-macros/` holds only the procedural macro entry point: a
  `proc-macro` crate exports only macros, so anything else here could not be
  called, tested, or measured from another crate.
- `crates/kaalang-render/` checks cycle boundaries and compacts a verified
  arrangement into the shared rows, columns, and routes every renderer starts
  from, cuts an empty preparation to its start, and places a type diagram's
  incoming cards in rows and columns under their headers.
- `crates/kaalang-svg/` measures the shared arrangement and renders standalone
  SVG without changing its structural layout, lists what each part of a diagram
  stands for in the source, and lays out and renders type diagrams.
- `crates/kaalang-testing/` holds the shared test material: the fixture corpus,
  generated performance probes and cycle shapes, and the budget harness. Only
  tests depend on it.
- `crates/kaalang-cli/` is the `cargo kaalang` subcommand, shipped as the
  `cargo-kaalang` binary. It resolves Rust paths through `kaalang-workspace`,
  where an editor asks rust-analyzer.
- `crates/kaalang-js/` exposes the compiler, the renderers, and the module tree
  walk of `kaalang-workspace` to JavaScript, as WebAssembly an editor's page and
  host load.
- `crates/kaalang/` exports the public macro and holds the test suite and the
  gallery in `examples/gallery/`. Its `.svg` files are generated by
  `just rust svg`.
- `ide/page/` is the page every supported IDE shows, in plain JavaScript.
  `ide/page/bench/` tries it in a browser with a stub host, and `checks.html`
  there plays its races.
- `ide/sample/` is the Cargo workspace every supported IDE opens for manual
  checks; its README lists the cases, and `just ide sample-check` keeps it
  building.
- `ide/vscode/` is the VS Code extension, in TypeScript: it shows the page in a
  webview, in place of a Rust editor or beside it.

Recipes live in `justfile` and `just/` and run from the repository root with
[just](https://just.systems); `just` and `just <module>` list them. Every recipe
runs in a Docker image built from `Dockerfile`, so the host needs only just and
Docker, but for two: the release recipes run cargo on the host for its crates.io
credentials, and `just ide vscode-open` opens the host's VS Code. The images
install the tools pinned in `mise/` with [mise](https://mise.jdx.dev). A recipe
rebuilds its image when those files change. Downloaded crates and npm packages
stay in the ignored `.cache/`, and the VS Code extension's dependencies in
`ide/vscode/node_modules/`.

## Compiler steps

| Step    | Implementation                                                                                                                                   | Algorithm                                                                                                                                                                                                    | Artifact                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Parse   | [`parse/`](../crates/kaalang-compiler/src/parse/mod.rs)                                                                                          | Validate each statement locally, flatten cycle bodies in source order, append the implicit end block.                                                                                                        | Parsed `Flow`.                                                                                   |
| Scope   | [`scope.rs`](../crates/kaalang-compiler/src/scope.rs)                                                                                            | Give cycle-local wires unique internal keys while retaining authored spellings; record the outer wires each cycle body captures.                                                                             | Scoped `Flow`.                                                                                   |
| Resolve | [`resolve.rs`](../crates/kaalang-compiler/src/resolve.rs)                                                                                        | Check that every capture names an earlier producer and that declarations and mutability agree.                                                                                                               | Wire-validated `Flow`.                                                                           |
| Analyze | [`analyze/`](../crates/kaalang-compiler/src/analyze/mod.rs), [`symbolic/validate.rs`](../crates/kaalang-compiler/src/symbolic/validate.rs)       | Validate reachability, captures, branch participation, placement, merges, and convergence over enumerated histories or exact execution conditions.                                                           | `Executions`, `Vec<WireMerge>`, and `Vec<ConvergenceGroup>`.                                     |
| Plan    | [`plan/`](../crates/kaalang-compiler/src/plan/mod.rs), [`symbolic/plan/`](../crates/kaalang-compiler/src/symbolic/plan/mod.rs)                   | Build a nested branch/join plan; independently replay it over the complete execution domain using the selected representation.                                                                               | `ExecutionPlan`, packaged with preceding artifacts as `Analysis`.                                |
| Project | [`topology/`](../crates/kaalang-compiler/src/topology/mod.rs), [`symbolic/projection.rs`](../crates/kaalang-compiler/src/symbolic/projection.rs) | Build nodes, exits, junctions, cycle boundaries, for-entry and for-end nodes, connections, back edges, and placement-only order. Preserve per-history transitive reduction when taking the connection union. | `Topology`.                                                                                      |
| Arrange | [`construct/`](../crates/kaalang-compiler/src/construct/mod.rs)                                                                                  | Find abstract ranks, columns, corridors, lanes, and cycle contours; independently verify the witness.                                                                                                        | Verified `Arrangement`; `build` packages it with `Analysis` and `Topology` as a `SemanticModel`. |
| Lower   | [`codegen/`](../crates/kaalang-compiler/src/codegen/mod.rs)                                                                                      | Emit hygienic Rust from the verified execution plan.                                                                                                                                                         | Lowered `ItemFn`.                                                                                |

[`analyze`](../crates/kaalang-compiler/src/lib.rs) returns an `Analysis` with a
verified plan without checking diagram realizability. `expand` checks the
expanded diagram before emitting Rust, then discards its arrangement; macro
expansion runs no compaction or SVG layout.

When a function or datatype has conditional parameters, the attribute lets rustc
evaluate their predicates before the compiler reads the signature.

For each local flow, `build_with_options` constructs the expanded projection
first, and a requested collapsed one only after it succeeds.

## Execution representation

[`analyze_local`](../crates/kaalang-compiler/src/lib.rs) selects one of the two
representations of
[RFC 0007 §5.1](rfcs/0007-language-refinements.md#51-finite-cycle-analysis): the
ordinary execution list for at most `ENUMERATED_HISTORY_LIMIT` histories,
otherwise the decision graph in
[`symbolic/condition.rs`](../crates/kaalang-compiler/src/symbolic/condition.rs).
When the product of declared alternatives exceeds the limit,
[`symbolic/walk/`](../crates/kaalang-compiler/src/symbolic/walk/mod.rs) counts
the actual domain first.

[`Executions`](../crates/kaalang-compiler/src/executions.rs) hides the storage
choice. `len()` counts without materializing summaries; its `Vec` interface
enumerates and caches the complete list, which can still be exponential. The
ordinary implementation is the reference for
[`symbolic/tests.rs`](../crates/kaalang-compiler/src/symbolic/tests.rs).

## Staged flows

The root `Analysis` and `SemanticModel` of a staged flow hold preparation; their
`stages` hold each stage's own, in declaration order.

Preparation is analyzed twice. The preliminary pass skips producer-usage checks
to find outer-plan bindings available on every completing route. Stage analyses
then determine which common wires they use; those dependencies are added to
preparation's transitions before the final pass checks usage.

| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Split   | [`parse/stage.rs`](../crates/kaalang-compiler/src/parse/stage.rs)                                                                                                                  | [RFC 0006 §2](rfcs/0006-stages.md#2-preparation-and-stage-declarations)                                                              |
| Analyze | [`stage.rs`](../crates/kaalang-compiler/src/stage.rs)                                                                                                                              | [RFC 0006 §6.1](rfcs/0006-stages.md#61-finite-analysis), [RFC 0007 §5.1](rfcs/0007-language-refinements.md#51-finite-cycle-analysis) |
| Arrange | [`topology/stage.rs`](../crates/kaalang-compiler/src/topology/stage.rs), [`construct/stage.rs`](../crates/kaalang-compiler/src/construct/stage.rs)                                 | [RFC 0006 §7.4](rfcs/0006-stages.md#74-composition-and-completion)                                                                   |
| Lower   | [`codegen/stage.rs`](../crates/kaalang-compiler/src/codegen/stage.rs)                                                                                                              | [RFC 0006 §6.2](rfcs/0006-stages.md#62-rust-lowering)                                                                                |

## Arrangement search

[`construct/`](../crates/kaalang-compiler/src/construct/mod.rs) runs the
decision procedure of
[RFC 0003 §2.1](rfcs/0003-svg-renderer.md#21-the-decision-procedure) under the
placement rules of
[§2.2](rfcs/0003-svg-renderer.md#22-branch-and-case-placement), trying the
arrangements of [§2.5](rfcs/0003-svg-renderer.md#25-presentation) first, with
the result junctions of
[RFC 0007 §6.2](rfcs/0007-language-refinements.md#62-result-junctions-and-construction)
and the for cycle placement of
[RFC 0008 §6.1](rfcs/0008-cycle-forms.md#61-expanded-for-cycle). Static
constraint contradictions can reject a topology before the sweep.

The separate exhaustive procedure under
[`construct/tests/reference.rs`](../crates/kaalang-compiler/src/construct/tests/reference.rs)
is a test oracle, not a runtime fallback. It shares topology facts and the
independent verifier with production, not transitions, pruning, column solver or
reconstruction. Positive-only preliminary attempts speed up witness discovery;
their exhaustion always falls through to the full enumeration. A bound on the
states it visits panics rather than count as a negative answer.

Exhaustive comparisons cover distributor bodies and ordered-question bodies and
count drawn, refused, and earlier-rejected outcomes separately. Neither domain
holds a refusal: validation rejects an exit enclosed between repeating routes
before construction. A separate test compares the production search with
memoization and separator refusal disabled. Mutated arrangements break
corridors, contours, lanes, and branch order, and the verifier must reject each.
Agreement supplements the coverage and soundness arguments of
[RFC 0003 §2.1](rfcs/0003-svg-renderer.md#21-the-decision-procedure); it does
not replace them.

The memo cache stops growing at `MEMO_CACHE_BYTES`. That limits a performance
optimization, not the search: a state it does not hold is explored again.

## Rendering steps

`kaalang-svg` keeps each diagram's steps in its own module, `flow/` and
`datatype/`, over the text measurement in `text.rs` and the SVG markup in
`markup.rs` that both share.

`kaalang-render`'s
[`ArrangementVerifier`](../crates/kaalang-render/src/verify/mod.rs) checks each
compaction candidate with the compiler's shared arrangement checks and the
cycle-boundary checks.

| Step                | Implementation                                                                                                     | Artifact                           | Specified by                                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Compaction          | [`compact.rs`](../crates/kaalang-render/src/compact.rs)                                                            | Compacted `Arrangement`.           | [RFC 0003 §2.3](rfcs/0003-svg-renderer.md#23-independent-checks)                                                                                                                                                   |
| Labels and captions | [`flow/captions/`](../crates/kaalang-svg/src/flow/captions/mod.rs), [`text.rs`](../crates/kaalang-svg/src/text.rs) | `Captions`.                        | [RFC 0002 §6](rfcs/0002-visual-language.md#6-wires-and-labels), [RFC 0005 §§4–5](rfcs/0005-markdown.md#4-presentation-and-accessibility), [RFC 0007 §6.4](rfcs/0007-language-refinements.md#64-oversized-formulas) |
| Pixel layout        | [`flow/layout/`](../crates/kaalang-svg/src/flow/layout/mod.rs)                                                     | `Scene`.                           | [RFC 0003 §2.4](rfcs/0003-svg-renderer.md#24-why-every-checked-arrangement-has-a-realization), [RFC 0007 §6.3](rfcs/0007-language-refinements.md#63-aligning-node-heights)                                         |
| Verification        | [`flow/layout/`](../crates/kaalang-svg/src/flow/layout/mod.rs)                                                     | Verified `Scene` or `StagedScene`. | [RFC 0003 §2.3](rfcs/0003-svg-renderer.md#23-independent-checks), [§4](rfcs/0003-svg-renderer.md#4-validation-and-failures)                                                                                        |
| Serialization       | [`flow/svg/`](../crates/kaalang-svg/src/flow/svg/mod.rs), [`markup.rs`](../crates/kaalang-svg/src/markup.rs)       | Standalone SVG `String`.           | [RFC 0003 §3](rfcs/0003-svg-renderer.md#3-svg-output)                                                                                                                                                              |

Before these steps, the compiler's
[`SourceFile`](../crates/kaalang-compiler/src/source/mod.rs) parses the Rust
file, removes what the compilation target does not compile, takes the flow at
the position the caller selected, builds its model, and cuts the text the
diagram quotes from its signature. The entry point
[`render_flow`](../crates/kaalang-svg/src/lib.rs) takes that flow. `kaalang-svg`
reads no source text; it reports a label's position from the span it received,
with the compiler's `line_and_column`. Positions need the compiler's `source`
feature, which the macro leaves off, since rustc gives it tokens.

Between verification and serialization `kaalang-svg` reads the hotspots it
returns beside the SVG from the verified scene in
[`flow/navigation.rs`](../crates/kaalang-svg/src/flow/navigation.rs). What a
node draws, where a producer binds its wire, and what a `return` hands to end
are the compiler's facts, in
[`source/spans.rs`](../crates/kaalang-compiler/src/source/spans.rs), and so is
the ribbon of each connection and merge, in
[`source/ribbons.rs`](../crates/kaalang-compiler/src/source/ribbons.rs). Neither
crate decides what a click does: that is the reader's. `Captions` keeps, with
every list of wire names a label draws, where each producer binds its wire; a
wire label records which list it draws, and the label module finds each name's
rectangle on its lines. `SourceFile::range` turns a hotspot's span into bytes of
the text as given.

## Type diagrams

A type diagram has no arrangement to decide or compact; its structure is the
incoming cards' rows and columns, which
[`card_cells`](../crates/kaalang-render/src/cards.rs) gives from each card's
group and a column count before any card is measured. The entry point
[`render_type`](../crates/kaalang-svg/src/lib.rs) takes the focus card and the
incoming cards from its caller, which reads each card's type through the
compiler's `SourceFile` for its compilation target and decides the relationships
each card draws into the focus. For the CLI and the bindings alike, the
`CargoTarget` of `kaalang-workspace` tells each target's group and crate name
from what `cargo metadata` lists, orders the cards' targets, and gives each
card's group, and `card_headers` of `kaalang-render` shortens their paths by
[RFC 0010 §2](rfcs/0010-type-card-paths.md#2-displayed-paths). A rendering error
names its card, so the CLI can name its file and the editor can leave an invalid
incoming card out. Beside the SVG the renderer returns the hotspots of
[`datatype/navigation.rs`](../crates/kaalang-svg/src/datatype/navigation.rs),
each with its card. Where each path stands in a field's type, where each
relationship names its target, and which relationships an editor's source
offsets identify are the compiler's facts, in
[`source/cards.rs`](../crates/kaalang-compiler/src/source/cards.rs).

[`datatype/mod.rs`](../crates/kaalang-svg/src/datatype/mod.rs) reads each card
from its type as the compiler read it and validates every label for XML,
[`datatype/layout.rs`](../crates/kaalang-svg/src/datatype/layout.rs) places the
cards and routes the lines by [RFC 0009 §4.2](rfcs/0009-types.md#42-structure)
and [§4.3](rfcs/0009-types.md#43-arrangement), and
[`datatype/svg.rs`](../crates/kaalang-svg/src/datatype/svg.rs) serializes them.

## IDEs

kaalang supports VS Code. Every supported IDE shows
[`ide/page/`](../ide/page/page.js), a page in plain JavaScript. It runs
`kaalang-js` in a worker, draws the flow or the type at the editor's cursor,
lists the ribbon of a clicked connection or merge, and asks its host to reveal a
range, to run the editor's own go-to action at a position, for the types of
values, and for the files that refer to a type, each with its references and its
place in the module tree; a host gives the text, the cursor, the target's cfg
set, and what the editor knows.

In VS Code, [`ide/vscode/`](../ide/vscode/src/target.ts) takes that set from
rust-analyzer, whose status report gives the set of each crate a file belongs
to, with its settings, the package's features, and build-script cfgs applied, so
that the diagram counts the code the editor shows as active. It asks again
whenever changes pause, since rust-analyzer changes the set as it loads the
workspace and reruns build scripts; until it answers, the diagram goes without
one. Cargo only lists the workspace's targets, without dependencies, so it
neither reads nor writes the lockfile; a target whose required features are off
is read too, as rust-analyzer reads it.

A type diagram's incoming cards come from rust-analyzer's references to the
focus; kaalang resolves no Rust path for the editor. A reference search stops at
a `use` that renames the type, so where one does, the host checks through
rust-analyzer's definition every relationship target in the targets' module
trees, which the bindings walk in a worker as the CLI walks them, the host
giving only file-system calls and the editor's unsaved texts. rust-analyzer
reads a file that several targets include in one crate, the first its status
report lists, so the host sends each file once, with that crate's set and place
in the module tree: code that crate leaves inactive, as the editor shows it,
draws no card, and neither do the other copies, which the CLI draws. The panel
follows Rust editors in the workspace folders and the sources their Cargo
targets include elsewhere. It opens what a click finds as the editor's own go-to
does, from where the cursor stands, so that the diagram follows only the target
and going back returns. In Restricted Mode it runs no cargo, whose binary the
workspace's configuration may name, and rust-analyzer does not run: what
rust-analyzer gives, the set, the types, incoming cards, module paths, and go-to
actions, waits for trust.

## Performance budgets

Each crate bounds the stages it owns: `kaalang-compiler` analysis, topology
construction, and lowering to Rust; `kaalang-render` structural compaction; and
`kaalang-svg` measurement and serialization. They share fixture sources and
generated probes through `kaalang-testing`, and the compiler and SVG corpus
budgets share one harness for warm-up, measurement, statistics, and the
aggregate and per-item checks.

The fixture corpus is read from the checked-in test fixtures, so it grows with
the language. Ordinary and stress fixtures run in separate corpus tests, each
with an aggregate budget of `count * allowance` and its own per-item limit. The
allowance is below the per-item limit, so the aggregate still catches
distributed regressions. Compiler passes take every fixture flow once; SVG
passes take expanded and collapsed diagrams of cycle fixtures. The render
crate's generated probes cover large compaction shapes outside the corpus.
